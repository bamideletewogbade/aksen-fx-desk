# Aksen OTC — change review since the deployment audit

Review snapshot: 5 October 2026, approximately 17:30 UTC. Baseline: the isolated source copy in `.audit/deployment-review-app` and [deployment-review.md](./deployment-review.md), prepared earlier today. This working tree is actively changing and has no new commit after the initial prototype, so this is a source-snapshot comparison, not a Git commit comparison. At the final comparison, 23 source files were added and 30 existing source files changed. The new Susu screens were written while this review was in progress.

## Decision

The product is more useful for a supervised demonstration. Clerk sign-in and onboarding, an operator chat quote path, cleaner desk/insights views, and a complete first Susu booklet flow are material additions. It is **not ready to become a real client's sole money ledger or automated WhatsApp channel**. The earlier critical FX, messaging and reconciliation issues remain, and Susu introduces another cash liability that is outside day close and the existing account ledger.

## Highest-priority findings from the delta

1. **P1 — Susu cash cannot be independently reconciled or corrected.** `recordCollection`, `closePage` and `withdraw` write booklet rows/audit events, but no cash-account movement is recorded in `src/server/day-close.ts` or the existing rails ledger. A dealer can record a collection or payout with an optional reference; there is no independent cash count, second approval, reversal/correction, duplicate collection key, or mismatch queue. Atomic database transactions prevent partial row writes, but they do not prove physical cash moved. Pilot only alongside the client's paper/cash book, with daily signed comparison, until these controls exist.
2. **P1 — Built-in credentials remain an alternative to Clerk.** `src/server/http.ts` resolves the legacy cookie first, and `src/app/api/auth/login/route.ts` and `signup/route.ts` remain live even if Clerk is configured. A Clerk-linked existing user retains their password hash. Thus switching on Clerk does not enforce verified email/MFA/recovery for every operator. Decide on one production auth policy and gate or retire the legacy routes for that environment. We verified source behavior, not a live Clerk tenant.
3. **P1 — A quote made from a chat can persist without successful delivery and can be associated with the wrong customer.** In `src/app/api/trades/route.ts`, the caller may supply both `customerId` and `conversationId`; `customerId` takes precedence without checking the chat's customer. `createQuote` commits before `attachQuoteToChat` links/sends. If linking or Twilio delivery fails, the API can report failure after leaving a real quote behind. Enforce chat-customer binding and use a durable outbox/idempotent retry for notification.
4. **P1 — The previous money and compliance blockers are unchanged.** `src/server/desk.ts`, `src/server/day-close.ts`, `src/app/api/channels/route.ts`, `src/app/api/twilio/inbound/route.ts` and the relevant funds/payout code in `src/server/trades.ts` were not repaired in this delta. The eight reproduction tests in `tests/deployment-audit.test.ts` still pass as demonstrations of defects, including post-refund credits and closed-day movement. Number ownership, KYC downgrade/late rejection, durable webhook recovery, test/live separation, late credits and reconciliation still require fixes. Provider eligibility remains a separate unresolved gate; see the earlier audit for external sources and exact use-case questions.
5. **P2 — Susu's "risk" score should not be sold as predictive intelligence.** `src/server/susu-ai.ts` sends a prompt asking for a probability of missed payments and displays either that score or a heuristic. There is no labeled outcome set, calibration test, cohort assessment, bias review, or measured precision. Present a transparent "needs a call" list based on missed days and last payment; disclose any model score as experimental and never use it to deny or alter a saver payout.
6. **P2 — Migrating during app startup has an operational race.** A normal local production build, sharing the active PGlite store, failed during `/onboarding` prerender with a duplicate `schema_migrations` type. An isolated PGlite build passed. The production Neon path was not tested, so this is not proof of a Neon failure. Still, `migrate()` creates the migration table before acquiring its advisory lock and every app instance runs migrations on cold start. Run migrations as one deployment step and test concurrent startup against a disposable Neon branch.

## Next acceptance sequence

First decide whether the initial client pilot includes Susu, FX, or both. For any real-money pilot, establish provider/channel eligibility and named business authorization, then repair the P1 items above and the earlier audit's FX blockers. Rehearse with a disposable production-like database and two real operator roles; verify a full quote/chat/funds/approval/payout/refund/day-close journey plus Susu collect/change/withdraw/rollover/cash count. Test failure and recovery: duplicate webhook, delayed bank credit, Twilio timeout, resend, concurrent payout, wrong customer attached to a chat, duplicate collection, and backup restore. Keep the client's current bank and paper records authoritative until every end-of-day balance is explained.
